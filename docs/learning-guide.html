1UML 읽는 법

이 가이드의 클래스 그림은 UML 클래스 다이어그램입니다. UML(Unified Modeling Language)은 프로그램 구조를 그림으로 나타내는 표준 표기법입니다. 상자 하나가 클래스 하나이고, 상자를 잇는 선이 클래스 사이의 관계입니다. 이 절의 그림 두 가지만 익히면 나머지 그림을 모두 읽을 수 있습니다.

표기뜻예
+public: 어디서나 쓸 수 있음+side(): Side
-private: 그 클래스 안에서만 씀-side: Side
#protected: 자식 클래스도 쓸 수 있음#directions(): int[][]
기울임꼴abstract: 몸체가 없어 자식이 반드시 구현+name(): String
밑줄static: 객체 없이 클래스 이름으로 부름+create(char, Side): Piece
이름: 타입필드의 이름과 타입, 메서드의 반환 타입+apply(Move): Board
«interface» «record» «enumeration»클래스 종류«record» Position
«utility»이 가이드의 약속: static 메서드만 모은 도우미 클래스«utility» Rules

2큰 그림: 계층과 패키지

개념 계층 구조 (Layered Architecture)

프로그램을 층으로 나누고 위층만 아래층을 부르게 하는 설계입니다. 아래층은 위층을 모르기 때문에 화면을 통째로 바꿔도 체스 규칙 코드는 고칠 필요가 없고, 규칙은 화면 없이 테스트할 수 있습니다.

이 구조는 세 가지 규칙으로 지킵니다.

  1. 아래층은 위층을 import하지 않습니다. 예를 들어 model은 다른 패키지를 전혀 쓰지 않습니다.
  2. Swing은 ui에서만, Gson과 파일 읽기·쓰기는 data에서만 씁니다. 나머지 패키지는 java.util만 씁니다.
  3. 화면 클래스(ui.screen)는 기능을 직접 부르지 않습니다. ChessBackend를 부르는 것은 컨트롤러(ui.controller)뿐입니다.

3상속과 다형성: 기물 클래스

개념 상속 (Inheritance)

공통된 부분은 부모 클래스에 한 번만 쓰고, 자식 클래스는 다른 부분만 씁니다. Java에서는 extends로 씁니다.

개념 다형성 (Polymorphism)

부모 타입 변수로 자식 객체를 다루면, 같은 메서드를 불러도 실제 객체에 맞는 코드가 실행됩니다.

체스 기물 6종류는 움직이는 방식에 따라 세 무리로 나뉩니다. 퀸·룩·비숍은 다른 기물에 막힐 때까지 미끄러지고, 킹·나이트는 정해진 칸으로 뛰고, 폰은 앞으로 가지만 대각선으로 잡는 자기만의 규칙이 있습니다. 이 무리가 그대로 클래스 계층이 됩니다.

  • Piece는 모든 기물의 공통 부분(진영, 이름, 기호, 가치)과 '갈 수 있는 칸'의 기본 계산을 가집니다.
  • SlidingPiece는 방향 목록 directions()만 받으면 막힐 때까지 미끄러지는 칸을 계산합니다.
  • StepPiece는 뛸 거리 목록 offsets()만 받으면 뛸 수 있는 칸을 계산합니다.
  • 그래서 Queen, Rook, Bishop, King, Knight는 방향이나 거리 목록과 이름·기호·가치만 정하면 됩니다.

직접 눌러 보기: 같은 메서드, 다른 결과

d4에 기물을 놓고 attackedSquares()(공격하는 칸)와 movableSquares()(갈 수 있는 칸)를 부른 결과입니다. 표시된 칸은 이 프로젝트의 Java 코드로 계산한 실제 값입니다.

다형성이 쓰이는 곳

합법 수를 만드는 Rules는 기물 종류를 묻지 않고 movableSquares()를 부릅니다. 실제로 실행되는 코드는 그 칸의 객체가 Rook이면 SlidingPiece의 계산, Knight면 StepPiece의 계산, Pawn이면 Pawn이 다시 정의한 계산입니다.

템플릿 메서드: 뼈대는 부모가, 빈칸은 자식이

Piece.movableSquares()는 '공격하는 칸 중 아군이 없는 칸'이라는 순서(뼈대)만 정하고, 공격하는 칸을 구하는 attackedSquares()는 자식에게 맡깁니다. SlidingPiece.attackedSquares()도 같은 방식으로 방향 목록 directions()를 자식에게 맡깁니다.

model/piece/Piece.java
public List<Position> movableSquares(Board board, Position from) {
    List<Position> result = new ArrayList<>();
    for (Position to : attackedSquares(board, from)) {   // 자식 클래스가 구현한 메서드
        Piece target = board.pieceAt(to);
        if (target == null || target.side() != side) {
            result.add(to);
        }
    }
    return result;
}
model/piece/SlidingPiece.java
@Override
public List<Position> attackedSquares(Board board, Position from) {
    List<Position> result = new ArrayList<>();
    for (int[] direction : directions()) {               // Rook은 4방향, Queen은 8방향
        Position next = from.offset(direction[0], direction[1]);
        while (next != null) {
            result.add(next);
            if (!board.isEmpty(next)) {
                break; // 기물에 막히면 그 칸까지만 공격합니다.
            }
            next = next.offset(direction[0], direction[1]);
        }
    }
    return result;
}

그래서 Rook 클래스는 이것뿐입니다. 실제 파일에서 줄 바꿈만 줄였습니다.

model/piece/Rook.java
public class Rook extends SlidingPiece {
    private static final int[][] DIRECTIONS = {{1, 0}, {-1, 0}, {0, 1}, {0, -1}};

    public Rook(Side side) { super(side); }

    @Override protected int[][] directions() { return DIRECTIONS; }
    @Override public String name() { return "룩"; }
    @Override public char symbol() { return 'R'; }
    @Override public int value() { return 500; }
}

새 기물을 추가한다면?

가상의 예로, (1, 3) 모양으로 뛰는 '낙타'를 추가한다고 해 봅시다. StepPiece를 상속해 offsets()와 이름·기호·가치만 쓰고, 기호로 기물을 만드는 Piece.create()에 한 줄을 더하면 이동 계산과 합법 수 판정, AI 탐색이 그대로 동작합니다. 기존 코드를 고치지 않고 기능을 늘리는 이런 성질을 개방-폐쇄 원칙(확장에는 열려 있고 수정에는 닫혀 있음)이라고 합니다. 다만 FEN 읽기나 기물 그림처럼 기호를 직접 다루는 곳은 따로 맞춰야 합니다.

4캡슐화와 불변 객체: 체스판

개념 캡슐화 (Encapsulation)

필드를 private으로 숨기고, 정해진 메서드로만 읽고 바꾸게 하는 것입니다. 객체가 자기 데이터를 스스로 지킵니다.

개념 불변 객체 (Immutable Object)

한 번 만들면 내용이 바뀌지 않는 객체입니다. 바뀐 내용이 필요하면 새 객체를 만듭니다. Java의 String이 대표적인 예입니다.

칸 하나: Position

Position은 열(col)과 행(row) 두 정수만 가진 record입니다. record는 모든 필드가 final인 값 클래스를 짧게 쓰는 Java 문법이라, 만든 뒤에는 값이 바뀌지 않습니다. 수를 나타내는 Move도 record입니다(Move.of("e2e4"), 승진은 Move.of("b7b8q")).

체스판 한 장면: Board

Board는 8×8 칸, 둘 차례, 캐슬링 권리, 앙파상 칸, 50수 규칙 카운터, 수 번호를 가집니다. 필드는 모두 private final이고 setter가 없습니다. 수를 두는 apply(move)도 원래 판을 바꾸지 않고 새 Board를 돌려줍니다.

처음rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1

FEN은 국면을 한 줄로 적는 표준 표기입니다. 대문자는 백, 소문자는 흑, 숫자는 빈칸 수입니다. 뒤쪽의 b는 흑 차례, e3는 앙파상 칸, 0과 1은 50수 카운터와 수 번호입니다.

apply(move)가 하는 일

  1. 2차원 배열을 복사합니다. 원래 판은 바뀌지 않습니다.
  2. 기물을 옮깁니다. 승진이면 Piece.create(승진 기호, 차례)로 새 기물을 놓습니다.
  3. 앙파상이면 옆의 상대 폰을 지우고, 킹이 두 칸 움직였으면(캐슬링) 룩도 옮깁니다.
  4. 캐슬링 권리, 앙파상 칸, 50수 카운터, 차례, 수 번호를 새로 계산해 새 Board를 만듭니다.

왜 불변으로 만들었나

  • 무르기가 쉽습니다. Game은 둔 수마다 Board를 목록에 모아 두고, 무르기는 목록 끝을 지우기만 합니다.
  • AI 탐색이 안전합니다. 수천 개의 수를 board.apply(move)로 '둬 보고' 평가해도 원래 판은 그대로라 되돌리는 코드가 필요 없습니다.
  • 버그가 줄어듭니다. 화면, AI, 채점이 같은 Board를 함께 봐도 누군가 몰래 바꿀 수 없습니다.

5추상 클래스: 레슨과 퍼즐

개념 추상 클래스 (Abstract Class)

공통 코드를 가진 '미완성' 부모 클래스입니다. abstract 메서드는 몸체가 없어서 자식 클래스가 반드시 구현해야 하고, 추상 클래스로는 객체를 직접 만들 수 없습니다(new TrainingSession() 불가).

레슨과 퍼즐은 둘 다 '보드에 수를 두면 채점하고, 틀리면 힌트를 주고, 필요하면 상대가 응수하는' 훈련입니다. 같은 부분은 TrainingSession에, 채점 방식처럼 다른 부분은 자식 클래스에 둡니다.

틀릴수록 자세해지는 피드백

  1. 1번째 오답"아쉽습니다! 다른 수를 생각해 보세요." 격려만 합니다.
  2. 2번째 오답힌트 칸을 강조합니다. 단계에 정해진 칸이 없으면 정답 기물의 칸입니다.
  3. 3번째부터정답 화살표를 그리고 출발·도착 칸을 강조합니다.

이 규칙은 부모의 applyWrongFeedback() 한 곳에만 있어서 레슨과 퍼즐이 똑같이 동작합니다.

7핵심 로직

이 절은 클래스 구조보다 '어떻게 계산하는가'를 다룹니다. 규칙 판정, AI, 퍼즐 채점 순서로 봅니다.

7-1. 합법 수 구하기 (Rules)

어떤 수를 둘 수 있는지는 세 단계로 걸러서 구합니다. 오른쪽은 그림 4의 국면에서 d4에 킹을 놓았을 때 단계마다 남는 수입니다.

model/Rules.java
public static List<Move> legalMoves(Board board) {
    List<Move> legal = new ArrayList<>();
    for (Move move : candidateMoves(board)) {     // 1~2단계: 후보 수
        if (keepsKingSafe(board, move)) {         // 3단계
            legal.add(move);
        }
    }
    return legal;
}

private static boolean keepsKingSafe(Board board, Move move) {
    Side me = board.turn();
    if (board.findKing(me) == null) {
        return true;                              // 킹이 없는 연습판은 항상 안전
    }
    return !isInCheck(board.apply(move), me);     // 둬 보고, 내 킹이 공격받으면 탈락
}

'일단 둬 보고 킹이 위험하면 버린다'는 단순한 방법이지만, 핀(움직이면 킹이 드러나는 기물)이나 체크 피하기 같은 어려운 경우가 저절로 해결됩니다. 불변 Board 덕분에 둬 보는 일이 안전합니다. ChessRulesTest는 시작 국면에서 3수 앞까지 나올 수 있는 국면 수가 표준값 8,902개와 같은지 확인합니다(퍼프트 검사).

7-2. 대국 결과 판정 (Game.status)

수를 둘 때마다 Game.status()가 위에서부터 차례로 검사해, 처음 맞는 것을 결과로 돌려줍니다.

  1. 기권한 쪽이 있음RESIGNED_WHITE / RESIGNED_BLACK
  2. 둘 수 있는 수가 없고 체크 중: 체크메이트CHECKMATE
  3. 둘 수 있는 수가 없고 체크가 아님: 스테일메이트(무승부)STALEMATE
  4. 양쪽 모두 메이트할 기물이 부족함DRAW_INSUFFICIENT
  5. 50수 동안 폰 이동·잡기가 없음 (halfmoveClock ≥ 100)DRAW_FIFTY_MOVE
  6. 같은 국면이 3번 나옴DRAW_REPETITION
  7. 체크 중이면 체크, 아니면 진행 중CHECK / PLAYING

7-3. AI: 국면 점수 (Evaluator)

AI는 국면을 숫자 하나로 바꿔 비교합니다. 점수는 항상 백 기준이라, 양수면 백이 유리하고 음수면 흑이 유리합니다.

점수 = Σ(백 기물 가치 + 위치 보너스) − Σ(흑 기물 가치 + 위치 보너스)
폰나이트비숍룩퀸킹
10032033050090020,000

위치 보너스: 나이트·비숍은 가운데에 있을수록, 폰은 앞으로 나갈수록 점수를 조금 더 받고, 킹은 가운데로 나오면 조금 깎입니다. 예를 들어 시작 국면은 0점이고, 1. e4를 두면 폰이 두 칸 전진하고(+10) 가운데에 가까워져(+4) 백 +14점이 됩니다.

7-4. AI: 미니맥스와 알파-베타 가지치기 (ComputerPlayer)

개념 미니맥스 (Minimax)

나는 내게 가장 좋은 수를, 상대는 내게 가장 나쁜 수를 둔다고 가정하고 몇 수 앞까지 모든 경우를 따져 보는 방법입니다. 백은 점수가 가장 큰 쪽(max)을, 흑은 가장 작은 쪽(min)을 고릅니다.

알파-베타 가지치기: 수 A를 다 계산하면 백은 '적어도 3점'을 확보합니다(α = 3). 수 B에서 흑이 −2로 가는 응수를 하나 찾는 순간, B는 아무리 좋아도 −2 이하라 A보다 나쁩니다. 그래서 B의 나머지 응수는 계산하지 않습니다. 결과는 미니맥스와 똑같고 계산만 줄어듭니다.

  • 계산 전에 수 목록을 섞습니다. 점수가 같은 수 중에서 매번 다른 수를 둬서 대국이 똑같이 반복되지 않습니다.
  • 메이트 점수는 100,000에서 몇 수째인지를 뺀 값입니다. 같은 메이트라도 더 빨리 끝내는 수를 고릅니다.
  • BooleanSupplier cancelled로 계산을 멈춥니다. 새 대국을 시작하거나 화면을 떠나면 바로 그만둡니다.

7-5. N수 메이트 계산 (MateSolver)

'N수 안에 체크메이트' 퍼즐은 상대가 어떻게 막아도 메이트가 되는지 확인해야 합니다. 공격 측은 통하는 수가 하나만 있으면 되고(OR), 방어 측은 모든 응수가 져야(AND) 합니다. MateSolver는 이 두 질문을 번갈아 하며 재귀로 내려갑니다.

  • findMateIn(board, N): 1수 메이트부터 N수 메이트까지, 체크하는 수부터 시도해 강제 메이트의 첫 수를 찾습니다. 퍼즐 힌트에 씁니다.
  • isForcedMate(after, 남은 수): 사용자가 둔 뒤, 남은 수 안에 메이트가 강제되는지 판정합니다.
  • bestDefense(after, 남은 수): 퍼즐에서 컴퓨터가 둘 응수입니다. 메이트를 피하는 수가 있으면 그중 점수가 가장 좋은 수를, 없으면 가장 오래 버티는 수를 고릅니다.
  • 계산이 1.5초를 넘으면 멈추고 '찾지 못함'으로 봅니다.

7-6. 퍼즐 채점 (PuzzleSession)

메이트 퍼즐은 정해진 수순이 아니라 N수 안에 메이트하면 정답입니다.

전술 퍼즐(최선의 수 찾기)은 정답 수순(solution)과 같은 수를 둬야 하고, 상대 응수도 수순에 적힌 대로 둡니다. 두 경우 모두 사용자가 둔 수는 무르기 스택에 쌓여 [무르기]로 되돌릴 수 있습니다.

  • 내 수가 끝나기 전에 상대 응수가 오면 이어서 재생합니다. 밀린 수가 더 쌓이면 마지막 수만 재생합니다.
  • 무르기·새 대국처럼 한 수로 설명되지 않는 변화는 바로 표시합니다.
  • 컨트롤러는 애니메이션을 신경 쓰지 않고 setBoard()만 부르면 됩니다.

9실행 흐름 따라가기

시퀀스 다이어그램은 객체들이 주고받는 메시지를 시간 순서대로 위에서 아래로 그린 그림입니다. 세로 점선이 각 객체이고, 실선 화살표는 메서드 호출, 점선 화살표는 돌려받는 값입니다. 번호는 호출 순서입니다.

AI 대전에서 한 수 두기

  • AI 계산(6~7)은 SwingWorker의 백그라운드 스레드에서 합니다. 그동안에도 화면이 멈추지 않고, 계산이 끝나면 화면 스레드에서 결과를 반영합니다(8~9).
  • 새 대국을 시작하거나 다른 화면으로 가면 '취소 신호'를 켜서 계산을 버립니다. 다시 돌아오면 onShow()가 AI 차례를 이어서 시작합니다.

레슨을 끝내면: 저장과 변경 알림

ChessBackend는 데이터를 바꾸는 메서드마다 끝에서 saveAndNotify()를 부릅니다. 저장한 다음 등록된 리스너를 모두 실행합니다. 메인 창은 시작할 때 자기 onDataChanged를 리스너로 등록해 두었습니다. 이것이 옵저버 패턴입니다.

service/ChessBackend.java
public void completeLesson(String lessonId) {
    if (!activeProfile().isLessonCompleted(lessonId)) {
        activeProfile().markLessonCompleted(lessonId);
        saveAndNotify();
    }
}

private void saveAndNotify() {
    save();                                          // storage.saveUserData(...)
    for (Runnable listener : List.copyOf(listeners)) {
        listener.run();                              // 등록된 쪽에 알림
    }
}
ui/MainFrame.java · 생성자 일부
backend.addChangeListener(this::onDataChanged);   // 데이터가 바뀌면 나를 불러 달라고 등록

12스스로 점검하기

발표에서 나올 만한 질문입니다. 답을 먼저 생각해 본 뒤 펼쳐 보세요.

Q1퀸·룩·비숍의 이동 계산 코드가 한 곳에만 있는 이유는?

세 기물 모두 '막힐 때까지 미끄러지는' 규칙이 같아서, 그 계산을 부모 SlidingPiece.attackedSquares()에 한 번만 썼기 때문입니다. 자식은 방향 목록 directions()만 정합니다(상속, 템플릿 메서드).

Q2Rules가 기물 종류를 몰라도 이동 칸을 구할 수 있는 이유는?

다형성 덕분입니다. Piece 타입 변수로 movableSquares()를 부르면, 실제 객체(Rook, Knight, Pawn …)가 구현한 메서드가 실행됩니다.

Q3왜 Pawn만 movableSquares()를 다시 정의했나?

다른 기물은 '공격하는 칸 = 갈 수 있는 칸(아군 칸 제외)'이지만, 폰은 앞으로 움직이고 대각선으로 잡아서 두 칸이 다르기 때문입니다. 그림 4에서 폰을 눌러 보면 공격하는 칸(c5·e5)과 갈 수 있는 칸(d5·c5)이 다릅니다.

Q4board.apply(move)를 부른 뒤 board는 어떻게 되나?

그대로입니다. Board는 불변 객체라 apply는 새 Board를 만들어 돌려줍니다. 그래서 무르기는 이전 Board를 다시 쓰면 되고, AI는 수를 마음껏 '둬 볼' 수 있습니다.

Q5킹이 공격받는 칸으로 가는 수는 어디서 걸러지나?

Rules.keepsKingSafe()입니다(합법 수 3단계). 그 수를 둔 판에서 내 킹이 공격받으면 후보에서 뺍니다. 기물 클래스의 movableSquares()는 기물 규칙만 봅니다.

Q6new TrainingSession()을 할 수 없는 이유는?

추상 클래스이기 때문입니다. 채점 방법(submitMove()) 같은 abstract 메서드는 몸체가 없어서, 이를 구현한 LessonSession이나 PuzzleSession 객체만 만들 수 있습니다.

Q7저장 방식을 데이터베이스로 바꾸려면 무엇을 고치나?

Storage를 구현한 새 클래스(예: DbStorage)를 만들고, Main에서 new JsonStorage(…) 대신 그 객체를 넘깁니다. ChessBackend와 화면 코드는 그대로입니다(의존성 역전).

Q8SettingsScreen이 ChessBackend를 모르게 만든 이유는?

MVC에서 View는 보여 주기만 하기 때문입니다. 판단과 기능 호출은 컨트롤러에 모여 있어서, 화면 코드는 단순해지고 기능을 바꿀 때 화면을 건드리지 않아도 됩니다.

Q9알파-베타 가지치기를 쓰면 AI가 고르는 수가 달라지나?

아니요. 결과를 바꿀 수 없는 가지만 건너뛰므로 미니맥스와 같은 수를 고르고, 계산만 줄어듭니다.

Q10레슨을 끝내면 왼쪽 프로필 카드 점수가 바로 바뀌는 이유는?

옵저버 패턴입니다. ChessBackend.completeLesson()이 저장한 뒤 등록된 리스너를 실행하고, 메인 창이 등록해 둔 onDataChanged가 카드와 모든 화면을 새로 고칩니다.

Q11AI가 생각하는 동안 화면이 멈추지 않는 이유는?

AI 계산을 SwingWorker로 백그라운드 스레드에서 하고, 결과만 화면 스레드에서 반영하기 때문입니다.

Q12새 화면을 하나 추가하려면 어떤 파일을 만들고 고치나?

ScreenId에 항목을 하나 더하고, XxxScreen(View)과 ScreenController를 구현한 XxxController를 만든 뒤, MainFrame에 register(…) 한 줄과 메뉴 항목을 추가합니다. 화면 전환 코드는 고치지 않습니다.
