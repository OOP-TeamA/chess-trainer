왜 이렇게 나눴나

  • 백프에게 학습 로직을 준 이유. 레슨, 퀴즈, 기보 맞히기는 이 프로그램의 핵심이고 화면과 로직이 가장 많이 맞물리는 곳입니다. 양쪽을 다 아는 사람이 로직을 맡아야 프2, 프3과 말이 잘 통합니다.
  • 백프에게 합치기를 준 이유. 교수님 안내의 “누군가는 양쪽을 다 이해해야 함”에 해당하는 자리입니다. 프1은 10~11주차에 메인 창과 체스판으로 가장 바쁘기 때문에 합치기까지 맡기기 어렵습니다.
  • 기보 파일 읽기를 백1에게 옮긴 이유. 기보 파일을 읽으려면 “이 수가 규칙상 가능한지”를 알아야 해서, 체스 규칙을 만든 사람이 맡는 게 가장 빠릅니다. 백2는 대신 추가·삭제 기능(교수님이 강조한 부분)에 집중합니다.
  • 시기별로 일이 몰리는 쪽이 다릅니다. 백엔드는 10~11주차에 바쁘고, 프론트는 12~13주차에 바쁩니다. 그래서 13주차에는 백엔드가 시연 영상과 내용 채우기를 더 맡도록 짰습니다.

조장과 짝

교수님 안내대로 조장을 둔다면 백엔드 조장은 백2(모든 데이터 구조를 알게 되는 자리), 프론트 조장은 프1을 추천합니다. 표의 “짝”은 자주 맞춰봐야 하는 상대입니다. 화면 하나마다 백엔드 짝이 정해져 있어야 “서로 상대가 할 줄 알았던 일”이 생기지 않습니다.

설계 문서와의 대응. 기능 명세서와 인터페이스 명세서의 A~F는 이렇게 바뀝니다: A → 백1, B → 백2(기보 파일 읽기는 백1로), C → 백3, D → 프1(저장소와 합치기는 백프로), E → 프2(화면)와 백프(로직), F → 프3(화면)와 백프(로직).

2.1개발 순서와 통합 기준

2026-11-04 기준 저장소에는 app/src/main/java/com/oopteama/chess/Main.java의 빈 Swing 창만 있습니다. 아래 순서는 계획이며 완료 현황이 아닙니다. Gradle 단일 app 모듈, 기본 패키지 com.oopteama.chess, Java 25를 구현 기준으로 사용합니다. 파일별 선행 작업은 7인 파일 흐름도, 첫 통합 입력과 예상 결과는 공용 샘플을 따릅니다.

순서·기한먼저 필요한 것동시에 진행할 일통합 통과 기준
0 · 11/6Java 25에서 빌드를 확인하고 패키지·공개 인터페이스를 맞춘다. Position, Move, RuleSet, 보드 입력, 레슨·용어·퀴즈·기록 저장의 최소 계약을 먼저 맞춘다.백프는 Gradle·테스트·계약을 정리하고, 백1은 엔진 골격, 백2는 텍스트 파일 로더, 프1은 메뉴·보드 모형을 만든다. 프2·프3은 가짜 데이터로 학습·용어 화면과 내용을 준비한다. 백3은 엔진 계약을 이용할 AI 골격을 만든다.gradlew.bat test와 gradlew.bat run이 실행되고, 홈·보드·레슨·용어 화면으로 이동한다. 계약 변경은 담당자에게 즉시 알린다.
1 · 11/9~11/11백1의 합법 수와 수 되돌리기 검증이 대국·퍼즐·기보의 선행 조건. 엔진이 늦어도 용어 퀴즈와 화면은 독립적으로 진행한다.백1은 기본 규칙과 시작 국면 perft, 백2는 기본 프로필의 레슨·퀴즈 기록 저장, 백프는 레슨 채점과 용어 4지선다 채점, 프1은 보드 클릭 입력, 프2·프3은 실제 데이터 연결을 맡는다. 백3은 검증된 엔진에서만 쉬운 AI를 연결한다.시작 국면 perft 깊이 1~3이 20·400·8,902이고, 레슨 1개·용어 검색·퀴즈 10문제를 각각 끝까지 실행한다.
2 · 11/13엔진·학습·저장 계약의 합의된 버전. 화면이 목업 대신 실제 로직을 호출해야 한다.백프가 매일 작은 변경을 합치고 금요일에는 전체 시연을 점검한다. 백1·프1은 대국을, 백2는 재시작 후 기록을, 백프·프2는 레슨과 퀴즈를, 백프·프3은 용어집을 붙인다. 백3은 쉬운 AI를 붙인다.공용 샘플로 홈 → 나이트 레슨 → 용어 검색 → 4지선다 10문제 → 재실행을 검증한다. 지정 답안 결과 7/10과 17점이 유지된다. 검증된 합법 수로 사람 대 사람 대국도 가능하다. 쉬운 AI가 준비되면 같은 흐름에 연결한다.
3 · 11/16~11/2011/13 흐름과 합법 수 검증. SAN·PGN 파싱은 엔진이 실제 수를 판별할 수 있을 때 착수한다.중간점검에서 쉬운 AI까지 시연하는 것을 목표로 한다. 점검 뒤 백1은 SAN·PGN, 백2는 추가·삭제 데이터, 백프는 퍼즐·기보 재생, 프2·프3은 해당 화면과 콘텐츠를 병렬로 만든다.중간점검 피드백과 빠진 기능을 기록한다. 11/20까지 번들 PGN 읽기가 막히면 번들 UCI 대안의 전제 조건을 확인한다.
4 · 11/25대국·학습·저장 흐름이 안정된 뒤 여러 사용자, 순위, 오답 노트, 즐겨찾기, 저장 대국을 연결한다.콘텐츠 확대와 UI 점검은 각 담당자가 병렬로 한다. 백프는 통합과 회귀 테스트, 백1·백3은 규칙과 AI 오류를 우선 고친다.발표 흐름을 새 컴퓨터에서 처음부터 끝까지 실행하고, 데이터 추가·검색·삭제와 재시작 후 유지까지 확인한다. 통과하지 못한 기능은 발표 화면에서 숨기고 목록에 남긴다.

의존 관계. 보드 모형과 콘텐츠 작성은 엔진과 병렬로 진행합니다. 실제 대국·퍼즐은 합법 수 검증 뒤, AI는 대국 상태가 연결된 뒤, SAN·PGN은 엔진이 수를 판별할 수 있을 때 합칩니다. 금요일 한 번에 병합하지 말고 통과한 작은 변경부터 통합합니다.
